# AI Insights & API Call Edges

## Goal
Two additions to code-map's graph:

1. **API call edges** — detect outbound HTTP calls (`fetch`, `axios`, `http.request`, etc.) in the codebase and draw them as a distinct edge type, so a frontend file calling `GET /users/:id` shows a visible connection to that endpoint — even though there's no `import` between the client code and the server route handler.
2. **AI-generated explanations** — let the user click an edge (import or API call) or a node and get a plain-English explanation of *why* that connection exists and what it means architecturally, generated by a local Ollama model so nothing leaves the machine and there's no API cost.

These are bundled in one plan because feature 1 feeds feature 2: once API-call edges exist, the LLM has something concrete to explain beyond "file A imports file B" — it can say "the dashboard fetches user data from the endpoint the auth service defines."

## Approach

### API call edges — detection strategy

Static, regex/AST-hybrid detection via ts-morph (already the analyzer's parser), not a runtime/dynamic trace. Three patterns to match, in order of confidence:

| Pattern | Example | Confidence |
|---|---|---|
| `axios.get/post/put/delete/patch(url, ...)` | `axios.post("/api/users", body)` | high — method is explicit |
| `fetch(url, { method: "..." })` | `fetch("/api/users", { method: "POST" })` | high if `method` present, else defaults to `GET` |
| `axios(url, { method: "..." })` / `axios({ url, method })` | | high |
| bare `fetch(url)` with no options | `fetch("/api/users")` | medium — assume `GET` |

URL extraction: only string literals and simple template literals with no complex expressions (e.g. `` `/api/users/${id}` `` → normalize to `/api/users/:param`) are captured. Calls whose URL is a variable with no literal in scope are recorded with `url: "<dynamic>"` and skipped from route-matching but still shown as an edge from the file (better to show an uncertain edge than silently drop a real API call).

**Route resolution (best-effort, not required for the edge to render):** if the codebase also defines server routes — Express-style `app.get("/api/users", handler)` / `router.post(...)` — the analyzer scans for those too and tries to match a client call's URL pattern against a registered route (accounting for `:param` segments). A match resolves the edge's target to the file that registers the route; no match renders the edge pointing to a synthetic "external endpoint" node labeled with the URL and method.

### AI explanations — approach

A local Ollama server (already running on this machine — confirmed `ollama list` shows `llama3.1:8b` and `nomic-embed-text` pulled) is queried on demand, not up front. Explaining all 25+ edges at load time would be slow and mostly wasted (most edges are never inspected). Instead:

- New server endpoint `POST /api/explain` takes `{ kind: "import" | "apiCall" | "node", id: string }`.
- The server assembles a small context bundle: for an edge, the source/target file paths, the imported symbols or HTTP method+URL, and a short snippet (first ~40 lines or the relevant import/call statement ± a few lines) from both files — not the whole file, to keep the prompt small and fast on an 8B model.
- That context is sent to `POST http://localhost:11434/api/generate` (or `/api/chat`) with a fixed system prompt instructing the model to explain the connection in 2-4 sentences, in plain English, referencing the actual file names and symbols given.
- Response is cached server-side in memory keyed by `(kind, id, contentHash)` so re-clicking the same edge doesn't re-query the model, and invalidated if the underlying graph is rebuilt.
- If Ollama isn't running or the model isn't pulled, the endpoint returns a 503 with a clear message; the UI shows "Ollama isn't running — start it with `ollama serve`" instead of a spinner that never resolves.

No embedding/RAG step for v1 — the context needed to explain a single edge is small enough to pass directly. `nomic-embed-text` is available if a later "ask a question about the whole architecture" feature wants semantic search over files, but that's out of scope here (see Out of Scope).

### Why local Ollama over a hosted API
No cost, no data leaving the machine (relevant since this tool by design points at arbitrary codebases, some private), and the user already has it running with a model pulled. Tradeoff: `llama3.1:8b` is noticeably weaker than a hosted frontier model at nuanced architectural reasoning — acceptable here because the ask is a short factual explanation of an already-extracted structural fact (an edge), not open-ended reasoning about the whole codebase.

## Changes Required

**Schema** ([src/types.ts](../src/types.ts), mirrored to [web/src/types.ts](../web/src/types.ts)):
- `ApiCallEdge`: `{ source: string; method: "GET"|"POST"|"PUT"|"DELETE"|"PATCH"|"unknown"; url: string; isDynamic: boolean; client: "fetch"|"axios"|"other"; target?: string /* resolved file id */ }`
- `FileGraph.apiCalls: ApiCallEdge[]` (new field alongside `edges`)
- `FileGraph.endpoints: { id: string; method: string; url: string }[]` — synthetic nodes for unresolved API targets (rendered as a distinct shape, not a `FileNode`)

**Analyzer** (`src/analyzer/`):
- New `apiCalls.ts` — walks call expressions for the patterns above, extracts method/URL/client, attempts route matching against any `routes.ts` output (see below)
- New `routes.ts` — scans for Express-style `app.<method>(path, ...)` / `router.<method>(path, ...)` registrations, used only as input to `apiCalls.ts`'s resolution step
- `fileGraph.ts` — call `apiCalls.ts` and attach results to the returned `FileGraph`

**Server** (`src/server.ts`):
- New `POST /api/explain` route
- New `src/llm/ollama.ts` — thin wrapper: `explainConnection(context): Promise<string>`, POSTs to `http://localhost:11434/api/generate`, handles connection-refused as a typed error
- In-memory `Map` cache for explanations, keyed by `${kind}:${id}:${hash(context)}`

**Frontend** (`web/src/`):
- `GraphCanvas.tsx` — render `apiCalls` as a third edge style (orange, dash-dot pattern, small method label like "GET" at the midpoint) alongside the existing import/type-only/cycle styles; render `endpoints` as diamond-shaped synthetic nodes
- `SidePanel.tsx` — add an "Explain this connection" button (visible when an edge, not just a node, is selected — requires promoting edge-click handling, since today only node clicks open the panel) that calls `/api/explain`, shows a loading state, then the returned text; cache client-side per session so re-selecting doesn't re-fetch
- `App.tsx` — needs edge-click state (currently only tracks selected node); add `selectedEdge` state and pass through
- `TopBar.tsx` — add an "API calls" toggle next to the existing "Cycles only" toggle, so the new edge type can be isolated the same way cycles can

**CLI** (`src/cli.ts`):
- `--ollama-model <name>` flag, default `llama3.1:8b`, passed through to `ollama.ts`
- `--no-ai` flag to skip wiring the `/api/explain` route entirely (useful if Ollama isn't installed)

## Cost & Services
- **Ollama**: free, runs entirely locally, no API key, no usage limit. The only "cost" is local compute/RAM (an 8B model needs ~5-6GB free RAM to run comfortably) and the one-time `ollama pull` disk space (~4.9GB for `llama3.1:8b`, already present).
- **No new paid services** for API-call detection — it's pure static analysis, same as the existing import graph.
- If a user doesn't have Ollama installed, the app still works fully for graph/import/API-edge features — only the explain button degrades to a clear error message, never a hard crash.

## Out of Scope
- Non-Express server frameworks (Fastify, Koa, Next.js API routes) for route resolution — v1 targets Express-style registration only; calls just render against synthetic endpoints for other frameworks.
- GraphQL query/mutation detection — a different shape of "API call" than REST verbs; would need its own detector.
- Whole-codebase Q&A / chat interface using `nomic-embed-text` for semantic search — the embedding model is available locally but wiring up a RAG pipeline is a separate, larger feature than per-edge explanations.
- Explaining symbol-level call edges (the function-call graph from the existing "Expand into functions" view) — this plan only covers file-level import edges and the new API-call edges.
- Any hosted/cloud LLM fallback if Ollama isn't available — by design this stays 100% local; a cloud fallback is a distinct tradeoff (cost, privacy) the user hasn't asked for.
